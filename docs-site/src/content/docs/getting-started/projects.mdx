A project is a folder: its editor, terminals, Git and search all work in that directory. Open one with `⌘O`, where you can also type a folder's path such as `~/code/app`, or from a terminal with the `sikemux` CLI:

```bash
sikemux .
sikemux src/App.tsx:42:5
```

Install the CLI from **Settings → Command line**.

## New and cloned projects

`⌘O` also starts a project from nothing. Type a name that matches no project, such as `Pinball Stats`, and pick **New project “Pinball Stats”**: Sikemux makes the folder `pinball-stats` with an empty git repository and opens it. Paste a repository's address instead, such as `git@github.com:team/app.git` or `https://codeberg.org/team/app`, and pick **Clone app**: the project opens at once and the repository comes down in the background, its progress at the end of the project's row in the side rail. If the clone fails, the row says so and hovering it says why; click it to close the project and remove its folder.

Both go in the folder you keep projects in: the first folder under **Settings → General → Project folders**, else the folder most of your projects are in, else your home folder, never inside another repository. A name that is taken gets `-2` after it. With a [linked host](/agents/linked-hosts/) in front, the project is made on that host. A clone signs in to the code host the way `git` on that host does, with its SSH keys or credential helper.

A repository you have on more than one host of your account is one project, with a copy on each; the side rail lists it once, and its tree switches between the copies. [On a server](/getting-started/install/#on-a-server) says how.

Sikemux is also listed under **Open With** in Finder and in apps that use it, such as Raycast. A folder opens as a project, and a text file opens in the editor of the repository it belongs to.

Markdown opens as it reads, and a `.dbml` schema opens as a diagram of its tables with a line between each pair of columns that refer to each other; **Source** above it shows the text. Drag the canvas or scroll to move around, pinch or scroll with `⌘` to zoom, drag a table to move it (where you leave the tables, and the pan and zoom, are kept across restarts), and point at a table to light up its relationships. Double-click a table to jump to it in the source, or the empty canvas to fit everything in view. An HTML file opens as its source; **Preview** above it draws the page as a browser would, with the styles and pictures beside it, and its web links open in your browser.

## Moving around

Swipe sideways with two fingers on the trackpad to move between a project's tabs, one tab per swipe.

The rail on the right has three pages, picked from the icons at its foot or by swiping across the rail:

- **Agents**: the project's chats, then the earlier ones.
- **Terminals**: every terminal open in the project.
- **Files**: the files open in the editor, then the project's file tree.

The tree opens its folders to the file in front. Drag a file or folder onto a folder to move it there, or onto the tree's empty space to move it to the project's folder; its open tabs and unsaved edits go with it. Files dragged in from Finder are copied, on this host only. Dropped anywhere outside the tree, a chat or a terminal, Finder's files go to the terminal you are typing in, else to the chat in front.

The sort button beside **Projects** in the side rail lists them by **Recent**, the one you last worked in first (the default), **Created**, the first you opened first, or **Manual**, the order you drag them in. Dragging a project puts the list in **Manual**.

Each project's row in the side rail shows the faces of its open agents, with a count of any past five, and a mark for how they stand together: working, waiting on you, or finished unseen. At the top of the **Agents** and **Terminals** pages, **All projects** counts what in other projects waits on you, and the Dock icon's badge counts it everywhere: a decision to make, such as a question, a permission or a pull request to merge; something only you can do, such as signing in, giving a secret or typing in a terminal; or something to fix, such as a failed turn or check. Work under way and finished turns don't count.

A terminal shows the folder its shell is in and how its last command went (running, done, or exit and its code) in its bottom corner. An SSH terminal's tab has a dot instead: green once connected, amber while connecting, red when it gave up. Closing a terminal's tab or pane, with `⌘W` or otherwise, ends its shell and anything running in it, without asking. A process's output tab is different: closing it leaves the process running.

## The Playbook

**Playbook** at the end of the project's tree in the side rail, `⌘⌥6`, or **Playbook** in the command palette opens the project's Playbook in a tab of its own. Its first pages hold what you decided once that every later agent goes by; [The Playbook](/agents/playbook/) describes them. Under a hairline come the project's settings:

- **General**: whether new chats start in a worktree, whether the project may start language servers, and the Space it sits under.
- **Processes**: the processes you added, each of which can be run, edited or removed, and **Add a process**, the same form as the run button's menu. Under them, the processes found in the build files, by folder, with a filter.
- **Setup**: what a new checkout of the project runs, what runs before one is removed, the ports each checkout gets and the heavy commands that take turns, all from `sikemux.json`, and whether that was proved on a fresh checkout. **Set up** hands the job to an agent, which writes `sikemux.json` and proves it; **Check again** proves it once more; when a step failed, its last line and **Open log** show under it, and **Fix with an agent** hands the failure to one. See [setting a project up](/getting-started/run/#setting-a-project-up).
- **Git**: the repository the project's Git views use, when its folder holds several.
- **sikemux.json**: whether the project has one, whether you trust it, and any mistakes in it. **Open** shows the file in the editor.

## A folder with several repositories

When the project folder is not a repository itself but holds several, such as `backend/` and `web/`, the Git pane lists them. Star one, or pick it on the Playbook's [Git page](#the-playbook), and it becomes the project's default: the Git pane opens it, the top bar shows its branch, the diff pane reviews it, and new agent worktrees are cut from it. When the folder holds only one repository, that one is used without asking. The choice stays on your Mac.

A project's checkout of its default branch, such as `main`, keeps up with the remote by itself: every ten minutes Sikemux fetches that branch and fast-forwards the checkout to it. It does so only when the checkout has no changes, no untracked files, no commits of its own and no merge or rebase under way, and no agent is at work in it; otherwise it leaves the checkout as it is. A checkout on any other branch, or one whose branch follows no remote, is never touched.

The Git pane's fourth page, **Pull requests** (`4`), lists the repository's open pull requests. One that is a slice's work shows the slice's mark, the gate it waits at, how many of its checks passed and failed, and a thumbnail of the picture its gate leads with; choosing it opens the chat of the agent working on it. One with no slice offers **review this** or **fix the comments**, which hands it to an agent in a checkout of its own as a new slice.

## Project config

Check a `sikemux.json` into a project to add actions, processes and a preview to the command deck (`⌘⇧P`). Sikemux shows each command and asks before running it.

```json
{
  "version": 1,
  "actions": [
    {
      "id": "check",
      "label": "Run checks",
      "command": "pnpm check",
      "placement": "terminal",
      "contexts": ["project"]
    }
  ],
  "tasks": [{ "id": "dev", "label": "Dev server", "command": "pnpm dev" }],
  "preview": { "url": "http://localhost:5173", "command": "pnpm dev" }
}
```

Processes go in its `tasks` list. Agents can start, read and stop them too. They keep running in the background while the window is closed.

`ports` and `env` give each checkout its own ports and environment, and `worktree` runs setup steps when a checkout is made and removed; see [each checkout's own ports](/getting-started/run/#each-checkouts-own-ports).

`ship` lists your project's own commands that put work live, such as `"ship": ["make deploy", "scripts/release.sh"]`, matched by their leading words: an agent running one waits for you to allow it first, like a deploy ([what leaves this machine](/agents/permissions/#what-leaves-this-machine)). Claude Code, Grok and Hermes catch them; other agents catch them only when the script runs a program Sikemux knows, such as `vercel`.

`heavy` lists the project's heavy commands, by the program and its first words, such as `{ "command": "pnpm test", "final": true }`. `pnpm test` then matches `pnpm test --run` and not `pnpm install`. An agent running one [waits its turn](/getting-started/run/#heavy-commands-take-turns) on the host with the built-in ones, such as `cargo build`; `"final": true` marks a check run before a commit, which goes ahead of the others. `{ "command": "jest", "light": true }` keeps a command out of the line, and `"heavy": []` turns the line off for the project. Never list a dev server or a watcher, which would hold its turn until stopped. A command run by its path, such as `./gradlew`, does not wait.

`resources` names what only so many agents can use at once, such as `"resources": { "port-3000": { "label": "The app on port 3000", "port": 3000 } }`. Each takes a `label`, a `count` (one unless you say), and an optional `port`, which Sikemux checks nothing else listens on before handing it out. A process or `heavy` entry lists what it holds while it runs in `needs`, such as `"needs": ["port-3000"]`: it starts once everything it needs is free, and lets go when it ends. Agents can also hold one for their turn; see [Things used one at a time](/getting-started/run/#things-used-one-at-a-time).

`planFirst` lists paths, such as `"planFirst": ["server/**", "db/schema.sql"]`, whose change Sikemux suggests planning before it starts, when what you type names one. Migrations folders, `.proto` and OpenAPI files, a top-level `server/` or `api/`, and UI folders such as `components/` count in every project without it.

### The project's check

`check` says what proves the project's work sound, which a board slice needs before it passes **Built**. Give it a command, which Sikemux runs on each commit on the project's branch, as committed:

```json
{ "version": 1, "check": "pnpm check" }
```

Or name the CI workflows that count, when the project's CI is its check:

```json
{ "version": 1, "check": { "ci": ["CI"] } }
```

Sikemux then reads the code host's runs on the project's branch as pushed, instead of building it, so the agent's commit has to be on that branch and pushed: an agent whose commit isn't is told to land and push it, and the slice waits until it is. Every workflow named has to pass on the pushed branch's newest commit, which holds the agent's. Other branches on the remote, such as work in progress, decide nothing. A run that is cancelled, or that doesn't start within a few minutes of the push, counts as no verdict, so the agent marks the card done again to have it checked.

A check command runs only once you trust `sikemux.json`: the first commit it would check asks you. While the file has a mistake, Sikemux reads no check from it, and an agent working a slice is told what is wrong rather than that the project names none.

When the full check is slow, name a quicker one beside it:

```json
{ "version": 1, "check": "pnpm check", "fastCheck": "pnpm check:quick" }
```

The fast check runs on each commit. The full check runs on the first commit after Sikemux starts, then again once three times its last length has passed, at least 5 minutes and at most 60, and on every commit while it is failing. Each run has `SIKEMUX_CHECK_SEED` in its environment, a number that stays the same for one agent and differs between agents, so a fast check can run a repeatable sample and agents together still cover everything.

When a check fails, Sikemux tests the commits since the last sound one to find the one that broke it, for up to 15 minutes, and tells only that commit's agent. If none can be singled out, one agent owns the failure and the others are told who.

Without a `check`, Sikemux uses the test command the project's build files suggest at its root: the `test` script in `package.json` (not the one `npm init` writes, which only fails), `cargo test` for a Cargo project, `go test` for a Go module, pytest or Django's tests for a Python project, and Maven's or Gradle's `test`. It reads them once, when Sikemux starts. This check runs only on a slice's latest commit when its agent marks it done, never on every commit, and never marks the project as broken. `"check": false` turns it off.

### The reservoir

When the work is a long list of separate problems, such as failing tests, name a command that prints them and Auto works through the list by itself:

```json
{ "version": 1, "reservoir": "scripts/failing-tests.sh" }
```

It prints one JSON object per line:

```json
{ "key": "parser/nested-loops", "title": "Nested loops fail to parse", "details": "See tests/parser/nested.c", "priority": 2 }
```

`key` names the item and must stay the same from run to run, and `title` says what it is. `details` and `priority`, a whole number where higher goes first, are optional. The command must exit with 0, so wrap a test runner that exits with an error whenever a test fails. Anything it prints on stderr is ignored unless it fails.

Sikemux runs it when Auto turns on, when Sikemux starts with Auto already on, and after each card Auto lands, one run at a time per project, for up to 30 minutes, at low priority, in a clean checkout of the latest commit of the branch Auto lands on. It runs only once you trust `sikemux.json`.

- The board holds at most 64 open cards from the reservoir, and tops them up after each landing, however long the list is. Items with the highest priority get a card first.
- Each key has at most one unfinished card. A key the command stops printing closes its card, unless an agent holds it.
- A key still printed after a card for it landed gets a new card, up to three landings, then rests until the command stops printing it. Marking a card done by hand leaves that key alone while it is still printed. Deleting a card lets its key come back on the next run.
- If the command fails, prints a line that isn't an item, or prints more than 64 MB, no card changes and Sikemux says why.

The title and details come from a command, so agents are told to read them as a description of the problem, not as instructions. Take `reservoir` out of `sikemux.json` to stop it; the cards already made stay. A card's run record says whether it came from the reservoir, and how long the runs its landing started took.

### Standing roles

A role is an agent that comes back as work lands, for a job that never finishes, such as keeping the docs true or merging duplicate code:

```json
{
  "version": 1,
  "roles": [
    { "name": "docs", "charter": "Keep docs-site true of what changed.", "every": 20 }
  ]
}
```

`name` is the role's own, `charter` is what its agent is asked to do, and `every` is how many commits must land on the branch Auto lands on between its runs. A project can name up to 16. Nothing runs unless a project names one, and a role runs only once you trust `sikemux.json`.

Auto counts from when the role first appears, and from where its last run ended, so a run's own commits don't count towards the next. Once enough have landed it adds a card, **Standing role: docs**, which a fresh agent takes through the usual path: a place among Auto's agents, a contract, a review and the merge queue. A role has one run open at a time. An agent that finds nothing to do ends its turn, its card closes as **Found nothing to do**, and that role then waits for twice as many commits until a run of it lands something.

### The changed page

When a slice's change touches the files a page is drawn from (`.tsx`, `.jsx`, `.vue`, `.svelte`, `.astro`, `.html` and stylesheets), Sikemux opens the page itself once the slice passes **Built**, in a new tab on its agent's desk, keeps screenshots of it at the tab's width and at a phone's and a tablet's as the slice's evidence, and closes the tab again. A tab the agent already has open on that site is used instead, and left open. It opens a server the agent started itself first. When the agent works in the project's own checkout, it opens the `preview` URL instead, if something is listening there, or else a server the project's run task started.

It opens a server's own address, or the `preview` URL when that names the same server, never the route the change touched, and it never starts a server. It takes nothing when no server is running, when the only server is in another checkout, or when the window is closed. It also takes nothing for a page that needs you to sign in first, for a change that isn't a web page, or when the server answers with a listing of its files or an error page instead of the page. These screenshots show the running thing, but they don't count as an assertion's evidence. `"preview": false` turns this off.

Sikemux versions before this one reject `false` for either field and ignore the whole file, so leave the field out until everyone working on the project has updated.

## Quitting

Terminals, agents and processes keep running when you quit, and come back where they were. **Quit and Stop Everything** (`⌥⌘Q`) ends them, and Sikemux stays stopped. Chats stay open asleep, each on its saved conversation with its name and tab, and start again only when you open or write to one: messages from agents and triggers wait for it until then. A turn they were in shows as stopped. Sikemux's window says it is stopped, with **Start Sikemux**, and nothing starts it again until you press that or start it another way. If Sikemux ever stops answering, its window says so, with **Restart Sikemux**: that ends it and starts it again. Terminals end; chats pick up where they were.

On a Mac, the window's close button hides Sikemux as `⌘H` does. Click it in the Dock, follow a `sikemux://` link or run `sikemux open` to bring the window back as you left it.
