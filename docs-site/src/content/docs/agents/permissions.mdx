Every agent starts within a launch boundary:

| Mode | What it does |
|---|---|
| **Normal** | The agent's own approval and sandbox behaviour: it asks before acting |
| **Auto** | The agent's own reviewer, a cheaper model, reads each action it would ask about, approves what is safe and asks you the rest |
| **YOLO** | Approvals and sandboxing are off: the agent acts without asking |

**Agents start in YOLO by default, on purpose.** Sikemux is built for agents that work on their own while you do something else. Change the default in **Settings → Permissions**, or pick **safe**, **auto** or **yolo** for one launch in the agent palette (`⌘⇧N`).

Auto is Claude Code's `auto` permission mode and Codex's `auto_review` approvals reviewer, in a chat and in a terminal tab. Other agents have no reviewer of their own, so Auto starts them in Normal. The reviewer runs on the agent's own account and counts toward its usage.

OpenCode has no YOLO mode, so it always starts in Normal. Pi has both in a chat; in its terminal it never asks, so there is no switch there.

A running chat can switch between its modes for agents that have them, from its composer, with `⌘⇧Y`, or with **Enable YOLO Mode** and **Disable YOLO Mode** in the agent's right-click menu. The switch applies to the running session at once and to the agent's next launch.

## What leaves this machine

Agents run in YOLO or Auto, so Sikemux's gate is the only sure stop: an agent's reviewer may approve a deploy, and the gate still holds it, and it stops only at a **production place**. A place is something an agent's action can change outside your Mac, listed on the project's [Playbook](/agents/playbook/) under **Places**. Sikemux lists the production ones from hard facts: the project's deploy config (`vercel.json`, `fly.toml`, `wrangler.toml`, `.firebaserc`, workflows that deploy to a production environment or publish a release, and the `ship` commands in [`sikemux.json`](/getting-started/projects/#project-config)), what a connector marks as production, such as a Rundeck job or a database, and what agents ran. You confirm the list once with **Looks right**; until then, every production place waits for you.

What an agent's action does:

| The action | What happens |
|---|---|
| Reads anything, or changes this Mac, a branch agents may land on, or a place that isn't production | It runs |
| Changes a production place at **Yours** | It runs |
| Changes a production place at **Tell me** | It runs, and you're told once it ends, with how it went |
| Changes a production place at **Mine** (every one, until you confirm the list) | One call, and the agent carries on with everything else |
| Sends something out that nothing can place | It runs, and is listed once on Places under **Seen, not gated**, with **Count as production**. The list never drops what you haven't looked at; past 64 it says how many more there were |

A production word anywhere in the action wins: `prod`, `production`, `prd` or `live` in a path, flag, bucket, context, profile, workspace, stack or remote makes it production, even when a place or a name like `staging` says otherwise. A stack, stage, app, Kubernetes context, AWS profile or Terraform workspace counts as production unless its name says it isn't, and so does one Sikemux can't read, such as a stage set from a variable. When the command names none, Sikemux reads the one the tool will use, such as the kube config's current context, the workspace selected in that folder or the default AWS profile, and names it on the call, which also offers **isn't production**. Your answer keeps it as a place with that exact context, workspace or profile as read from that config file or folder, so the next action there goes by its level without asking afresh, and the same name read elsewhere still asks. A name that says production is never offered **isn't production**. Reads, such as `kubectl get`, `terraform plan`, `helm list`, `vercel ls`, a `--dry-run`, a GraphQL query or a `SELECT`, never reach the gate (`dev`, `staging`, `qa`, `test`, `preview`, `sandbox`, `demo`), and `kubectl`, `helm`, `terraform`, `aws` and the hosting tools ask when nothing names where they land.

**One call per piece of work at a place.** The call shows what the change is and where it lands, and every agent waiting on the same work there shares it. For a deploy, your yes covers that work's deploy there: every command it takes and its retries, however they're spelled, until the end of the turn in which the agent hears it. Anything else at a production place, such as a database write, a publish, a store upload or a Sikemux tool call, your yes covers once, exactly as the call showed it; an agent sends a migration's statements together, so it is one call. The work is everything the agent's checkout changes against the branch it lands on, committed or not, by content: a new commit or edit is new work, and a rebase that changes nothing of it isn't. If the work changes while the call waits, Sikemux withdraws the call and the next try asks again; where the folder isn't a repository, each action asks by itself. A yes given before Sikemux restarted, for something that hadn't run, passes nothing. A no holds for that work at that place, however the action is spelled, until the work changes or you write to the agent again; its retries raise no new card, and your own words on the call are a no with directions. Nothing passes on a timeout. Places are your project's: an agent changing folder doesn't leave them behind.

The call shows at the end of the agent's own [chat](/agents/chats/#when-the-agent-asks-you-something), in the title bar's count of the project's calls, on the notch and above the composer of its chat in the phone app, with **Change** the place and **Not now** as its options, and **Go with this** to answer. Words typed in its chat never pass it: only the button does, and your own words on it are a no with directions. Answer in any of them and it leaves them all.


**A yes lands only on a call you've seen, by its button.** Sikemux checks that the answer came from the app, the notch or your paired phone, not a program on your Mac; that the client had shown you the call; and that the work is still the work the call showed. Typing "ship it to prod" in a chat passes nothing: the agent raises the call, and your tap is the yes. A production place's level loosens only by your own tap on Places.

Pushes are read the way git resolves them. A push that only reaches a branch of the agent's own runs. One that reaches the project's branch follows the Playbook's [Landing](/agents/playbook/#landing): where agents land their own work, it goes. Each ref a push carries is judged by itself, so a tag pushed beside the branch counts as a tag. Where the release workflow tells tags apart, as nightly and stable tags, each kind is a place of its own on Places; a call for one that recurs, such as a nightly, offers **from now on just tell me**, which moves it to Tell me. A tag counts as a release where a workflow publishes releases, and a push to a remote that isn't the project's code host, such as Heroku or Dokku, is a deploy to that app. Whatever Sikemux can't show stays off the default branch, a release branch and every tag counts as reaching them.

`gh workflow run` is read as GitHub will run it, from the default branch or `--ref`, not from the copy in the checkout. It asks when the workflow publishes, deploys by a known step or by a command the gate would hold or that says production, names a production environment, or is named or given inputs that say release, deploy, publish or prod, read or not. A job that calls another workflow in the repository is read too. Any other workflow run is listed under **Seen, not gated**; `gh run rerun` runs.

What Sikemux reads as leaving this machine:

- **Pushing** commits with `git push`, `git_commit` with `push`, or a git alias for a push, and **merging** a pull request: `gh pr merge`, `glab mr merge` and Bitbucket's merge tool.
- **Deploying**: `vercel --prod`, `--target`, `promote`, `redeploy`, `alias` and `rollback`, `netlify deploy --prod`, `fly deploy`, `firebase deploy`, `wrangler deploy`, `railway up`, `heroku container:release`, `dokku`, `kubectl apply`, `create`, `replace`, `edit`, `rollout`, `set`, `delete`, `scale` and `patch`, `helm install`, `upgrade`, `uninstall`, `delete` and `rollback`, `terraform apply` and `destroy`, `pulumi up` and `destroy`, `cdk`, `sst` and `sam deploy`, `serverless deploy`, `aws cloudformation`, `ecs`, `lambda` and `s3` writes, `eas update`, `gh workflow run`, a script named for deploying or releasing, such as `./deploy.sh` or `npm run deploy`, and Vercel's promote and redeploy tools and Rundeck's run tool. Your project can add its own with `ship` in `sikemux.json`; each becomes a production place.
- **Publishing**: `npm`, `pnpm`, `yarn` and `changeset publish`, `cargo publish`, `twine upload`, `uv` and `poetry publish`, `gem push`, `docker push` and `docker buildx build --push` to a registry that isn't this Mac's, `gh release create` and `edit`, `gh api` writes, `eas submit` and `eas build --auto-submit`, and Google Play's upload tool. Runners such as `npx`, `pnpm dlx` and `bunx` are read for the program they start.
- **Changing production data**: any statement an agent runs on a database you marked **Production** ([Databases](/agents/databases/)), `supabase db push` and `prisma migrate deploy` against a database on another computer, and `psql` or `mysql` to another computer, which is seen unless a production database place names it.
- **Writing to a website** in the agent's browser tabs: clicking the submit button of a form that doesn't use GET, `browser type` with `submit` or `browser press` Enter in a field of such a form, the same steps in `browser act`, and a `browser evaluate` script that calls `fetch` or `XMLHttpRequest` with a method other than GET, HEAD or OPTIONS, `sendBeacon`, `form.submit` or `requestSubmit`, or clicks a submit button. A search box and any other GET form are not writes.
- **Writing through a connector**: Jira's create, edit, comment, transition, worklog and link tools, and Bitbucket's comment, create issue, create pull request, edit pull request, review, decline and issue state tools. Reading through them is free.
- **Sending data with `curl` or `wget`**: a method other than GET, HEAD or OPTIONS, or a data, form or upload flag, to a host that isn't this computer.

Nothing sent to `localhost`, `127.*`, `::1`, a `.local` name or a `file:` address is held, and neither is anything from the pages Sikemux shows you itself.

Sikemux catches these where agents run commands: it stands in for each of those programs on every agent's `PATH`, so agents in chats and in terminal tabs are both held, and a chat with Claude Code, Grok or Hermes also checks each shell command before it runs. A process an agent starts in Sikemux, by its command or one from `sikemux.json`, is checked the same way before it starts. The person's answer reaches an agent in a terminal tab as a message, typed in once it is waiting for one. What it doesn't catch:

- `ssh`, `scp` and `rsync` to a server: git runs `ssh` itself, so these aren't read at all;
- a program run by its full path, such as `/opt/homebrew/bin/vercel --prod`, by Codex, OpenCode, Pi or OMP in a chat, or by any agent in a terminal tab;
- a script that sets its own `PATH` before deploying, unless your project lists it under `ship`;
- code that calls a deploy service's API itself, or a cloud SDK with its own credentials;
- `curl` or `wget` written so their flags or address can't be read, such as through a variable or a config file, or any other program that sends data. Reading a command line can always be got around;
- a button that isn't a form's submit button, even when the page's own code saves something when it's clicked, a form inside a frame from another site, and Space on a focused submit button;
- in `browser evaluate`, a write the page's own code makes after it has waited on something, since by then the agent's script is no longer what's running, and a script that sets out to avoid the check, such as by taking `fetch` from a new frame;
- anything sent by a GET request, including data put in an address, an image or a link the agent opens with `browser navigate`, and anything sent over a WebSocket, by `browser upload` or by dragging;
- a script reading a token or other secret from a page. Only sending is held;
- connector tools outside the list above, such as Bitbucket's rerun and stop pipeline.
