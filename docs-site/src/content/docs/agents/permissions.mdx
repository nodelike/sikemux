Every agent starts within a launch boundary:

| Mode | What it does |
|---|---|
| **Normal** | The agent's own approval and sandbox behaviour: it asks before acting |
| **Auto** | The agent's own reviewer, a cheaper model, reads each action it would ask about, approves what is safe and asks you the rest |
| **YOLO** | Approvals and sandboxing are off: the agent acts without asking |

**Agents start in YOLO by default, on purpose.** Sikemux is built for agents that work on their own while you do something else. Change the default in **Settings → Agents → Launch boundary**, or pick **safe**, **auto** or **yolo** for one launch in the agent palette (`⌘⇧N`).

Auto is Claude Code's `auto` permission mode and Codex's `auto_review` approvals reviewer, in a chat and in a terminal tab. Other agents have no reviewer of their own, so Auto starts them in Normal. The reviewer runs on the agent's own account and counts toward its usage.

OpenCode has both in a chat, as rules on its session; what your own OpenCode config denies stays denied in YOLO, and its terminal keeps your own permissions. Pi has both in a chat; in its terminal it never asks, so there is no switch there.

A running chat can switch between its modes for agents that have them, from its composer, with `⌘⇧Y`, or with **Enable YOLO Mode** and **Disable YOLO Mode** in the agent's right-click menu. The switch applies to the running session at once and to the agent's next launch.

## What leaves this machine

Agents run in YOLO or Auto, so Sikemux's gate is the only sure stop: an agent's reviewer may approve a deploy, and the gate still holds it, and it stops only at a **production place**. A place is something an agent's action can change outside your Mac, listed on the project's [Playbook](/agents/playbook/) under **Places**. Sikemux lists the production ones from hard facts: the project's deploy config (`vercel.json`, a `fly.toml`, `wrangler.toml` or `.firebaserc` app whose name says production, workflows that deploy to a production environment, stable release tags, and the `ship` commands in [`sikemux.json`](/getting-started/projects/#project-config)), a database you marked **Production**, and what agents ran. You confirm the list once with **Looks right**; until then, every production place waits for you.

What an agent's action does:

| The action | What happens |
|---|---|
| Reads anything, or changes this Mac, a branch agents may land on, or a place that isn't production | It runs |
| Changes a production place at **Yours** | It runs |
| Changes a production place at **Tell me** | It runs, and you're told once it ends, with how it went |
| Changes a production place at **Mine** (every one, until you confirm the list) | One ask, and the agent carries on with everything else |
| Sends something out that nothing can place | It runs, and is listed once on Places under **Seen, not gated**, with **Count as production**. The list never drops what you haven't looked at; past 64 it says how many more there were |

Something counts as production only when it is known to be: a place on your list, a database you marked **Production**, a vendor's own production flag such as `vercel --prod`, or a production word, `prod`, `production`, `prd` or `live`, in a path, flag, bucket, context, profile, workspace, stack or remote. That word wins even when a place or a name like `staging` says otherwise. A stack, stage, app, Kubernetes context, AWS profile or Terraform workspace whose name says nothing, a package registry and a GitHub release all run, and are listed under **Seen, not gated** until you count one as production. When the command names no context, workspace or profile, Sikemux reads the one the tool will use, such as the kube config's current context, and judges that name. Reads, such as `kubectl get`, `terraform plan`, `helm list`, `vercel ls`, a `--dry-run`, a GraphQL query or a `SELECT`, never reach the gate.

**One ask per piece of work at a place.** The ask shows what the change is and where it lands, and every agent waiting on the same work there shares it. For a deploy, your yes covers that work's deploy there until the end of the turn in which the agent hears it. Anything else at a production place, such as a database write or a publish, your yes covers once. The work is everything the agent's checkout changes against the branch it lands on, committed or not, by content: a new commit or edit is new work, and a rebase that changes nothing of it isn't. If the work changes while the ask waits, Sikemux withdraws the ask and the next try asks again; where the folder isn't a repository, each action asks by itself. A yes given before Sikemux restarted, for something that hadn't run, passes nothing. A no holds for that work at that place until the work changes or you write to the agent again; its retries raise no new card, and your own words on the ask are a no with directions. Places are your project's: an agent changing folder doesn't leave them behind.

The ask shows at the end of the agent's own [chat](/agents/chats/#when-the-agent-asks-you-something), in the title bar's count of the project's asks, on the notch and above the composer of its chat in the phone app, with **Change** the place and **Not now** as its options, and **Go with this** to answer. Words typed in its chat never pass it: only the button does, and your own words on it are a no with directions. Answer in any of them and it leaves them all. After a no to publishing a release, the agent can ask again once the tag moves or you approve another release there.


**A yes lands only on an ask you've seen, by its button.** Sikemux checks that the answer came from the app, the notch or your paired phone, not a program on your Mac; that the client had shown you the ask; and that the work is still the work the ask showed. Typing "ship it to prod" in a chat passes nothing: the agent raises the ask, and your tap is the yes. A production place's level loosens only by your own tap on Places.

Pushes are read the way git resolves them, in the repository they run in: a push after `cd`, `pushd` or `env -C`, or inside a subshell, is judged against that repository, not the project's. A push that only reaches a branch of the agent's own runs. One that reaches the project's branch follows the Playbook's [Landing](/agents/playbook/#landing): where agents land their own work, it goes. Each ref a push carries is judged by itself, so a tag pushed beside the branch counts as a tag. Where the release workflow tells tags apart, as nightly and stable tags, each kind is a place of its own on Places; an ask for one that recurs, such as a nightly, offers **from now on just tell me**, which moves it to Tell me. A tag counts as a release where a workflow publishes releases, and a push to a remote that isn't the project's code host, such as Heroku or Dokku, is a deploy to that app. A push or delete of many refs that waits counts them and says why the agent needs it; refs that are neither branches nor tags don't ask. Whatever Sikemux can't show stays off the default branch, a release branch and every tag counts as reaching them.

`gh workflow run` is read as GitHub will run it, from the default branch or `--ref`, not from the copy in the checkout. It asks when the workflow names a production environment, or is named or given inputs that say production. A job that calls another workflow in the repository is read too. Any other workflow run is listed under **Seen, not gated**; `gh run rerun` runs.

What Sikemux reads as leaving this machine, which asks only when it reaches a production place:

- **Pushing** commits with `git push`, `git_commit` with `push`, or a git alias for a push, and **merging** a pull request: `gh pr merge`, `glab mr merge` and Bitbucket's merge tool. Pushing the production branch of a project Vercel deploys counts as deploying it, like `vercel --prod`.
- **Deploying**: `vercel --prod`, `--target`, `promote`, `redeploy`, `alias` and `rollback`, `netlify deploy --prod`, `fly deploy`, `firebase deploy`, `wrangler deploy`, `railway up`, `heroku container:release`, `dokku`, `kubectl apply`, `create`, `replace`, `edit`, `rollout`, `set`, `delete`, `scale` and `patch`, `helm install`, `upgrade`, `uninstall`, `delete` and `rollback`, `terraform apply` and `destroy`, `pulumi up` and `destroy`, `cdk`, `sst` and `sam deploy`, `serverless deploy`, `aws cloudformation`, `ecs`, `lambda` and `s3` writes, `eas update`, `gh workflow run`, a script named for deploying or releasing, such as `./deploy.sh` or `npm run deploy`, and Vercel's promote and redeploy tools and Rundeck's run tool, which wait when they reach Vercel's production or a job Rundeck marks as production. Your project can add its own with `ship` in `sikemux.json`; each becomes a production place.
- **Publishing**: `npm`, `pnpm`, `yarn` and `changeset publish`, `cargo publish`, `twine upload`, `uv` and `poetry publish`, `gem push`, `docker push` and `docker buildx build --push` to a registry that isn't this Mac's, `gh release create` and `edit`, `gh api` writes to a repository other than the project's own, and `eas submit` and `eas build --auto-submit`. Runners such as `npx`, `pnpm dlx` and `bunx` are read for the program they start.
- **Changing production data**: any statement an agent runs on a database you marked **Production** ([Databases](/agents/databases/)), `supabase db push` and `prisma migrate deploy` against a database on another computer, and `psql` or `mysql` to another computer, which is seen unless a production database place names it. SQL sent to a Supabase project through its API asks first, unless it only reads or uses the read-only query endpoint.
- **Writing to a website** in the agent's browser tabs: clicking the submit button of a form that doesn't use GET, `browser_type` with `submit` or `browser_press` Enter in a field of such a form, the same steps in `browser_act`, and a `browser_evaluate` script that calls `fetch` or `XMLHttpRequest` with a method other than GET, HEAD or OPTIONS, `sendBeacon`, `form.submit` or `requestSubmit`, or clicks a submit button. A search box and any other GET form are not writes. On a registrar's or DNS host's panel, a submit, through the browser or `curl`, and a click that saves through the page's own script wait for your yes.
- **Sending data with `curl` or `wget`**: a method other than GET, HEAD or OPTIONS, or a data, form or upload flag, to a host that isn't this computer.

Nothing sent to `localhost`, `127.*`, `::1`, a `.local` name or a `file:` address is held, and neither is anything from the pages Sikemux shows you itself.

Sikemux catches these where agents run commands: it stands in for `git`, the deploy tools (`gh`, `vercel`, `kubectl`, `helm`, `terraform`, `aws` and the other hosting tools) and `psql` and `mysql` on every agent's `PATH`, so a deploy a script starts is checked too, and a database client waits only when it reaches a database you marked **Production**, and a chat with Claude Code, Grok or Hermes also checks each shell command before it runs. A process an agent starts in Sikemux, by its command or one from `sikemux.json`, is checked the same way before it starts. The person's answer reaches an agent in a terminal tab as a message, typed in once it is waiting for one. What it doesn't catch:

- `ssh`, `scp` and `rsync` to a server: git runs `ssh` itself, so these aren't read at all;
- a program run by its full path, such as `/opt/homebrew/bin/vercel --prod`, by Codex, OpenCode, Pi or OMP in a chat, or by any agent in a terminal tab;
- a publish or a `curl` started by a script rather than typed by the agent;
- a script that sets its own `PATH` before deploying, unless your project lists it under `ship`;
- code that calls a deploy service's API itself, or a cloud SDK with its own credentials;
- `curl` or `wget` written so their flags or address can't be read, such as through a variable or a config file, or any other program that sends data. Reading a command line can always be got around;
- a button that isn't a form's submit button, even when the page's own code saves something when it's clicked, except on a registrar's or DNS host's panel, a form inside a frame from another site, and Space on a focused submit button;
- in `browser_evaluate`, a write the page's own code makes after it has waited on something, since by then the agent's script is no longer what's running, and a script that sets out to avoid the check, such as by taking `fetch` from a new frame;
- anything sent by a GET request, including data put in an address, an image or a link the agent opens with `browser_navigate`, and anything sent over a WebSocket, by `browser_upload` or by dragging;
- a script reading a token or other secret from a page. Only sending is held;
- connector tools other than a database query, Vercel's promote and redeploy, and Rundeck's run: Jira, Bitbucket and Google Play's upload go without an ask.

## Changes to CI

Where agents push to GitHub with an App of their own, their key can't change files under `.github/workflows/`, so Sikemux pushes those changes itself. A workflow change waits for you when the file mentions secrets, an environment or `id-token`, or lets its own token write to the repository. The rest go out by themselves. A waiting commit is left out of the agent's push and everything else goes around it, except the agent's commits that can't go without it.

You get one ask per agent, in its chat, on the notch and on your phone: "@Name wants to change CI:" with the commit's subject, what it changes, and the diff under **What runs**. A new waiting commit from the same agent joins that ask. **Push the change** makes Sikemux push what the ask lists, with a key that can change workflows, made for that one push and revoked straight after. No agent ever holds that key. **Don't push it** leaves the commits on this Mac, and the agent is told to revert them.

Every push goes out through Sikemux. If an agent runs `git push` with a change that waits for you, the push is turned back and the agent is told to push with `git_commit` and `push: true`. A project without the App works as before.

## How agents push

Agents push with `git_commit` and `push: true`. From an agent's own checkout, a push without a land sends the agent's own branch, never the project's. From the project's own checkout, the push first runs the same checks as a land, and commits that fail them stay unpushed with what failed; an agent's raw `git push` of a branch there is turned back and pointed at `git_commit`. Tags, and pushes from your own terminals, go through as usual. A land without a push says plainly that it is only in this computer's checkout, not on the remote. A refused push shows the reason the hook or the remote gave.

Each commit an agent makes ends with `Agent:` and `Agent-Signature:` lines. `git config sikemux.attribution false` in a repository, or with `--global` for every one, leaves them off, the land queue's commits included. Who made each commit is then kept in a local git note, so goal summaries and `who_wrote` still show it.

After an agent pushes, Sikemux watches that push's CI itself. A failed run wakes the agent with the failing jobs named, or its lead once the agent has closed, or the project's chief once the lead has closed too. Other ends wake nobody.
