Start an agent with `⌘N`. Each agent opens in the chat Sikemux draws for it. Its agent starts as you begin writing, so a chat you open and leave empty runs nothing. An agent that went to sleep shows its chat as it was and wakes as you begin writing to it.

## GUI and TUI

The **GUI / TUI** switch at the top of an agent swaps between:

- **GUI**: Sikemux's chat, with the transcript, tool calls, questions and the composer.
- **TUI**: the agent's own terminal interface, running in a Sikemux terminal.

Switch while the agent is idle: while it works, the switch is greyed out until it finishes its reply.

What you typed but did not send comes with you. A draft in the composer waits at the TUI's prompt, unsent, and what is typed in Claude's input box comes back to the composer.

## The composer

- `↑` in an empty box brings back what you sent before, and `↓` goes forward again.
- `/` at the start of a message lists Sikemux's own commands, then the session's commands and skills. `/side` opens a side chat (see below), `/model` opens the model picker, `/clear` starts a fresh chat with the same agent, account and model, `/fork` goes on in a new chat that takes this one's words along, and `/yolo` turns asking before acting off or on. A session command or skill you pick goes in as a chip, like a mention. A command the session doesn't have isn't sent: it stays in the draft, and the composer says so.
- `@` names another agent, in this project or any other, or an earlier chat to open again. A closed agent keeps its name, so `@` finds it by that name and opens its chat again.
- `#` hands over a GitHub, GitLab, Bitbucket or Forgejo issue, and `!` a pull request.
- `+` attaches a file or folder from the project.
- Drag an agent or chat from the tab rail onto a composer to hand it over as context. An open agent goes in as an `@` chip at the cursor, and the agent you are writing to learns how to read what it said; a closed chat opens again for the message, as with `@`. A teammate on another host goes in by its name and host; another host's agents outside your team can't be handed over.
- `&`, or **Stash** beside **+**, opens your [Stash](/getting-started/stash/), what you shared to Sikemux from your phone; the item you pick goes into the message as a chip. `⌘S` stashes the message you are writing for later.
- A picture you paste, drop or add with the `+` button is numbered, and shows up as **Image 1**, with a small copy of the picture, where the caret was. The agent sees each picture at that spot in your message, just as a terminal agent would. Click a picture above the box to see it at full size. On your phone a picture you add is named the same way, as **[Image #1]** where the caret was; delete the tag and the picture comes off the message.
- On a Mac, the camera beside the mic takes a **SnapShot**: a picture of the window you were in just before Sikemux, such as a browser or a simulator, put in the draft like any picture; hover it to see which app's window it takes. `⌘⇧2` does the same from any app, sending the window in front to the project's front chat, bringing Sikemux forward and saying which chat it went to; change the keys under Keyboard shortcuts. The agent is also told the app's name and the window's title, and, when Sikemux is allowed **Accessibility** in System Settings > Privacy & Security, the text the window shows and where each piece sits. The first SnapShot asks for **Screen Recording**; allow it, then quit and reopen Sikemux. SnapShots need macOS 14 or later.
- What you pick stays in your message as a chip. Backspace once selects a chip, and again removes it.
- On your phone, `@`, `#`, `!` and `+` open the same lists above the composer; tap a kind at the top to switch to it. A backspace into a chip there removes it at once.
- The ring beside the model shows how full the agent's context is. For Claude Code it fills toward where Claude will compact the conversation on its own, which is your `autoCompactWindow` setting if you set one, less the room Claude keeps back, rather than toward the model's whole window; hover it for the tokens, where it compacts out of the whole window, and what the session has cost. Once Claude Code, Codex or Muse has compacted the conversation to make room, the ring holds how many times, and its card says when it last did. Many compactions in one chat mean the agent has lost detail, so a fresh chat may serve better.
- `/compact` summarizes the conversation so far to free up context, in every chat agent, each with its own compaction: Hermes calls it `/compress`, and `/compact` runs that. A Claude Code chat over 150K tokens left idle compacts by itself while its prompt cache is still warm, before it sleeps or before the cache's hour runs out, so coming back to it later does not send the whole conversation again uncached. The chat you see keeps every message either way.
- When the chat's model can run faster, the foot of the model menu has a **Standard | Fast** switch. Claude Code offers it on the models it lists as supporting fast mode, Codex on the models it lists a faster service tier for, so it follows each agent's own list. Fast answers sooner and costs more; it applies from the next turn and lasts for that session, and the switch shows once the chat has started.
- Once a Claude Code or Codex reply ends, the empty box may show what the agent expects you to send next, with `Tab` after it. `Tab` puts it in the box to change or send; `Esc` hides it until the next reply. It goes when you type, attach something, or the agent asks you something. Claude Code only offers one from the second reply on. For Codex it costs one short, low-effort model call after each reply, and older Codex versions offer none.
- Selections from terminals, problems and logs can be sent to any agent. They land in its draft, or are typed into its CLI when it runs in its terminal.

## While the agent works

| You press | What happens |
|---|---|
| `Enter` | Sends it now, steering the agent in the middle of its reply |
| `⌘Enter` | Your message waits and is sent when the agent finishes its reply |
| `⌘Enter` in an empty box | Sends the messages that were waiting, now |
| `Esc` in an empty box | Stops the agent's reply |

To swap the two, set **Settings → Chats → Sending while an agent works** to **Queue**. An agent that can't be steered always queues. Sending from your phone follows the same setting.

The line under the reply says what the agent is on: the step of its plan, or else the command it runs, the agent it waits for, or why it retries, and for how long.

## How a chat stands

The last line of every chat says how its turn stands, in one of six states:

| State | Says | What you can do there |
|---|---|---|
| **Working** | the step of its plan it is on, and for how long | |
| **Waiting** | what it waits on, such as CI, a deploy, another agent or a set time, and how long that has gone against how long it usually takes | |
| **Needs you** | the question or permission it waits on, and for how long | **Look** |
| **Done** | where the work is (no changes, uncommitted, committed, landed, on staging, shipped) and how its checks went | the next step, such as **Commit**, **Push**, **Deploy to staging**, **Ship to production…** or **Roll back** |
| **Stopped** | what it left open, with nothing set to wake it | **Carry on** |
| **Failed** | why, such as Claude's usage limit and when it resets | another account, sign in, retry, or reconnect |

On your phone the same line ends the chat, with the same buttons; over a call docked in the chat it says only **Needs you** and how long the call has waited. A step's button sends that step to the agent as your message. The purple one is the next step that needs no call; **Ship to production…** never ships by itself, it raises a call you answer first. An agent running in its terminal (TUI) shows the same words after its name at the top of the pane.

## Triggers

An agent can set a trigger on its own chat, to be sent a prompt later: once, such as "check the deploy in 20 minutes", or on a schedule, such as every hour or each weekday at 9:00. Ask it to, in your own words.

Its triggers are listed above the composer, each with when it next fires. **×** removes one. When a trigger fires, its prompt arrives in the chat in a bubble at the left under the trigger's name, and an agent that was asleep wakes for it. A time that passes while the host is off fires once the host is back: a one-time trigger always, a repeating one only within 15 minutes of its time.

An agent that pushed can end its turn on CI instead of watching it: its trigger fires once CI on that commit ends, with how it went. When the CI ends, you get one notification, but none on a phone that has that chat open.

The same goes for anything else an agent waits on. Rather than checking again and again, each check a turn that costs tokens, it parks on a build or other run it started, ending its turn until the run finishes or prints what it waits for, or on another agent, until that agent finishes or asks you something. Sikemux starts its next turn when that happens, saying what happened, or after a timeout, two hours unless the agent sets another. While it waits, the chat says what on.

Closing the agent pauses its triggers, and a toast says how many with **Undo**, which opens the chat again. **Recent** keeps the chat while they wait, with a clock and their count on its row, and taking it up again, from **Recent** or by an agent resuming it, starts them again: a repeating trigger skips the times that passed while it was closed, and a one-time trigger that came due meanwhile fires once, saying when it was due. A webhook trigger keeps its address, and the requests that arrive while the chat is closed wait for it: taken up again, it gets each in turn, the last 10 at most, and is told how many older ones were dropped. Paused triggers still count toward the 20 a chat holds. Rest the pointer on that row to see them; **×** beside one removes it for good.

For recurring work that shouldn't depend on one chat, such as triaging new issues every morning, ask the agent to give the trigger to the project rather than its chat. Each time it fires, it adds a card to the project's board as if you added it, so Auto starts an agent on it when Auto is on. While the card it added last is still open, a firing goes to that card instead of adding another, and the agent working it is told, so the same work never starts twice. These triggers, like every other, are listed on the [Playbook](/agents/playbook/#automation)'s Automation page, where you can pause or remove one; they stay after the agent that set them closes.

## Editing a message you sent

In a Claude Code, Codex, Muse or Pi chat, click the pencil under a message you sent, **Edit message**, while the agent is idle. Change it and press `Enter`; `Esc` leaves it as it was. The chat goes back to that message: the replies after it are dropped, and your new text is sent in its place.

## Replying to an answer

Hover over the end of an agent's answer and click the arrow beside the copy button, **Reply**. The answer is quoted above your draft; the × takes it off. When you send, the agent gets the quoted words with your message, so it knows which answer you mean, and your sent message shows one line of it above the text.

## Side chats

To ask something aside without derailing a chat, type `/side` in it, or `/side` and your question. A new chat opens beside it with the same agent, account, model and project, and is listed under the main chat. Its first message carries the main chat's latest exchanges and tells the agent how to read more of it; the main chat carries on and isn't told. The side chat's header says **side of @Name**; click it to go back to the main chat. On the phone, send `/side` the same way and the side chat opens.

## Subagents

When an agent hands part of its work to subagents, each one shows in the chat as a card with its name, its task and how it stands: working, done, failed, lost or stopped, with its tool calls and tokens. Click a card to see what that subagent did. While any are still working, they are also listed above the composer, where **×** stops one of Claude Code's alone and the chat works on without it.

## Messages between agents

When agents on a team message a chat, what they say folds to one line, so your prompt and its answer stay close together. The line shows who wrote, how many messages there are, the latest of them and how long it went on. Click it to open it where it is, on the last five messages; **Show N earlier** brings the rest.

Everything in a turn another agent started folds except that turn's last message, and a message that arrives while the agent answers you folds on its own. Whatever stays in view ends the line, so a long job reads as its answers with one line between each. When someone in a line needs you, because it asked you something, waits on a permission, failed its turn or stopped, the line says so in red until that is settled.

What wakes an agent without you, such as a trigger, a teammate's report or Sikemux's own note, waits 30 seconds after the agent's last turn ends, so what arrives close together is read in one turn. Your messages and answers to an agent's question go at once. After 20 turns in a row that nobody wrote, the rest wait for you, except reports from the agent's own workers: the agent shows as needing you in the inbox, and anything you write to it lets it go on.

An agent that has been working for 30 minutes without calling a tool, such as one stuck behind a queued build, is said to be stalled. Sikemux tells its lead once, which wakes the lead; an agent with no lead, or whose lead is asleep or stopped, shows in the inbox under **Needs you** instead, until it calls a tool again or its turn ends.

Once your last message has scrolled off the top of the chat, a strip over the transcript says what you asked. Click it to go back to that message.

## Sharing a chat

The share button at the top of a chat makes a link to it. Pick how long the link works, 1 hour, 24 hours or 7 days, and **Create link**. Anyone signed in to Sikemux who has the link can read the chat as it happens, from its start. They see everything the agent read and ran, including what's in your files, so share with care. While it is shared, the button shows how many people are watching; click it to copy the link again or **Stop sharing**.

People with the link can also write to the agent, while your computer is online, and give a name to sign it with. Sikemux can't check that name, so it always shows marked as a guest's, such as "Alex · guest". Their message doesn't reach it straight away: it waits over your composer under **From guests**, on the Mac and the phone, and they see it waiting too. You get a notification, and the agent shows as needing you until you deal with it. **Send** gives it to the agent as your own message, running with the chat's current permission mode, so read it first; **×** dismisses it. Up to 10 wait at once, of up to 10,000 characters each. They can't answer the agent's questions or attach files. Stopping the share dismisses whatever still waits.

## Code in a reply

When Sikemux leaves sentences out of an answer because they rest on no source, a quiet line under the answer says how many, such as **2 sentences with no source left out**. **Show** puts them back where they stood, faint, and **Hide** takes them out again; this works on your Mac and your phone, and a shared chat's page lists them under the answer.

A code block in a reply shows its language's icon at the top. The wrap button beside it wraps long lines to the chat's width, and the copy button copies the code, showing a tick once it has. A long block scrolls inside itself when a scroll starts over it.

## Pages in a reply

An agent can answer with a page it built, such as a chart, a table or a comparison, drawn right in its reply. Hover the page for **Open in tab**, which opens it on the agent's desk; on Linux it sits under the page. A mockup of a whole screen, app or site opens in a tab on the agent's desk instead, at full width, and the reply shows a card with a picture of it; **Show** brings that tab forward, or opens it again if it was closed. A reply draws at most 4,000 px of a page: a taller one fades out at the cut on a Mac, with how much it shows and **Open in tab** under it. Clicking a page never takes the keyboard from the composer.

## MCP apps in a reply

Some MCP servers give a tool a page of its own, an [MCP App](https://github.com/modelcontextprotocol/ext-apps). When a Claude chat calls such a tool, the reply shows the page in place of the call, in a card that names the server and the tool. **Expand** in the card's corner grows the app over the whole chat, still running as it was, and Esc or **Collapse** puts it back; an app can ask to grow itself too. It needs Claude Code 2.1.301 or newer, and works with any MCP server Claude is set up with.

The app runs in a sandbox of its own: it keeps no cookies or storage, can reach only the domains its server declared, and can't open windows or leave its card. It can call its own server's tools, through the chat's agent and under the chat's permissions, read that server's resources, and ask for a link to open on the agent's desk. It can't reach any other server or the agent's conversation. Calls it makes don't go into the conversation either. While the chat's agent isn't running, the app can still show what its call returned, but its own calls are refused until you send a message.

Only the apps you can see run. One you scroll past turns into a picture of itself after a moment and stops running, and at most three run at once however long the chat is. Scroll back and it starts again from its call's result, so anything you'd changed in it that its server doesn't keep starts over.

## Schemas in a reply

When an agent writes a database schema in a ` ```dbml ` code block, the chat draws it as a diagram of its tables and the references between them. A scroll that starts over it pans the diagram, and one that starts elsewhere keeps scrolling the chat; pinch or `⌘`-scroll zooms, and tables drag. While the agent is still writing it, the diagram only grows, so it holds still between tables. **Fit** shows every table again and **Arrange** lays them out afresh. **Source** shows the DBML, the copy button copies it, and **Open on desk** opens it on the agent's desk, as a diagram with room to spread out and its DBML a click away.

## Diagrams in a reply

When an agent writes a ` ```mermaid ` code block, such as a flowchart, a sequence, class, state or ER diagram, a pie chart or a Gantt chart, the chat draws it as a diagram in your theme's colours. It draws it once the agent has finished writing the block, which shows its text until then. A diagram wider than the chat shrinks to fit. **Source** shows the Mermaid text and **Diagram** the drawing again; the copy button copies the text. A block that isn't a diagram Mermaid can draw stays as text, with **Can't draw** above it, and pointing at that says why. On the phone, a Mermaid block shows as its text.

## Math in a reply

When an agent writes LaTeX math, the chat typesets it. A formula on its own between `$$` signs or `\[` and `\]`, or in a ` ```math ` code block, is drawn centred in your theme's ink once the agent has finished writing it; double-click it to see its LaTeX, and point at it for the copy button. A block that isn't math Sikemux can typeset stays as text, with **Can't typeset** above it, and pointing at that says why. Math between single `$` signs or `\(` and `\)` inside a sentence is written in its line, such as `α² ≤ 1/n`, with letters in italic, names such as log upright and a script Unicode has no letters for set smaller, so it wraps with the words around it. On the phone, math shows as its LaTeX.

## GIFs

An agent can send a GIF, which shows where it sent it with **Powered by KLIPY** beneath it. When a turn's work folds away, its GIFs stay in view above the reply. It doesn't show up as a step in the chat, and the agent doesn't mention it.

## Why something is as it is

Ask an agent why something in the project is as it is, such as a file, a few of its lines, a commit, a call or a rule, and it can look it up in what Sikemux keeps: the commits that made it and the agents that wrote them, what you asked those agents before, the calls you answered, your rules and what was decided. It answers from those, and each claim carries a small chip of what it rests on: **your message**, **the change** (and whether it landed), **your answer**, **your rule** or **decided**. Click a chip to open it: the chat at that message, the commit in Git, the Playbook's rules, or the chat of the agent that asked the call.

In such an answer, a sentence of plain words that sits beside sourced claims but rests on none of them is left out, and a quiet line under the answer says how many: **2 sentences with no source left out · Show**. **Show** puts them back where they were, in faint text; **Hide** takes them out again. Questions, code, quotes, tables, headings and anything with its own formatting are never left out. If Sikemux restarts while the agent is still answering, that answer gets no chips and nothing is left out of it.

## Long chats

On a wide window, **Settings → Appearance → Chat width** lets a chat's messages and composer grow wider than their reading width: **Comfortable** keeps them to a reading column, **Wide** to half as wide again, and **Full** to the whole pane.

A chat holds only the part of its transcript near what you're reading, so a long one stays quick. Scroll up and earlier turns come back as you reach them, and the find bar searches the whole chat. A chat that is asleep, as resumed tabs are until you select them, shows its history, scrolls and finds without starting its agent.

## @Chief

Every project has a chief, @Chief: one chat that stays with the project, where you say what you want and it starts and steers the agents that do the work. Its row is the first in the project's list in the tab rail, with Sikemux's purple S where other rows have a face, and what it is on beside its name. The row is there from the start; the chat is made the first time you open it or write to it, and spends nothing until then. Closed, it comes back as itself when you open it again.

The chief runs on the agent and model a new chat in the project would use, and its chat's header says which, with the project and how many agents it has: **storefront · 14 agents · Opus 5.5**. The agents it starts are listed under it as any team is. Opening a worker's chat shows the chain down to it in the header, such as **@Chief › @Rohan › Stripe webhook retries**, and what you type there goes to that worker. The composer says so, **Send to @Rohan · @Chief is told**: the chief hears what you wrote with its next turn.

The first time you open a project's chief, it writes to you first: who it is, the chats open in the project and how each stands, and what waits on you. Your chats stay where they are, and you can still talk to any of them.

When you come back to the chief after an hour or more, a **While you were away** card sits at the end of its chat. It holds the calls that wait on you, one open and the rest folded under it; what agents decided for you, each with **Overrule**; and what landed, with **Try it** where there is something to try. It stays until every call in it is answered, or, with none, until you next write to the chief.

**Overrule** sends the decision back to the agent that made it and leaves one line in the chief's chat. When Sikemux kept a rule from it, the line says decisions like that come to you from now on. **Undo** on that line puts the decision back. An Overrule that stopped Auto's run can't be put back: its line says so and offers no Undo.

On Monday mornings, the chief's chat shows a count of last week when anything was decided or answered: **Last week I decided 212 things, and you overruled 3. You answered 12 of 14 calls as I picked.**

In **All projects**, each project's @Chief leads that project's agents, with the project's name beside it. The project that most needs you comes first: one with a call open or an agent that needs you, then one with work under way, then the rest. The island over the notch lists them the same way.

## Agent names

Each agent gets a one-word name when it starts, an anime character's such as Luffy or Frieren, that no other agent in its project has, open or closed. To name new agents after nature instead, such as Otter or Maple, set **Settings → Chats → Agent names** to **Nature**. Agents already open keep their names, and so does any agent you renamed.

A chat keeps its agent and its name when you close it and open it again, from **Recent**, **Undo**, a link or `@`. Only when another open agent of the project holds that name by then does it come back under a new one. Names are reused only once the list runs out, the name of the chat closed longest first, and a name you chose is never reused. Clicking a closed agent's name, such as on a message it sent or a decision in a goal, opens its chat again.

When you name an agent with `@` in a message, or another agent messages it, a band of light passes once over its row in the tab rail and on the island.

The tab rail lists the agents that need you first, then those at work, each keeping its place while it works, then the finished and idle ones, the one you last wrote to first. An agent working or messaging other agents on its own never moves an idle one up the list.

Each row ends with one mark for how its turn stands, the same on the island and your phone: the agent's own working mark while it works; a ring that fills as a wait on CI runs, with the minutes left beside it once Sikemux knows how long that usually takes; the pink timer with when a set wait ends; an amber dot with how long it has waited on you; a purple dot when it is done, a red one when it failed, and a hollow ring when it stopped with work left and nothing set to wake it. Point at a row for its card, which says it in words, such as **needs you 12m** or **CI 4m**, and with the line its chat ends with.

To change a chat's title, double-click it in its header or in the tab rail, type, and press Return; Escape leaves it as it was. **Edit Title…** in its right-click menu does the same.

## Earlier chats

**Recent** in the tab rail lists the project's earlier chats, newest first. Scroll to its foot and older ones load, a page at a time. ⌘⇧N lists them too, beside the agents already open: pinned first, then newest first, and typing narrows the list without reordering it. A chat that ran in a worktree is listed under its project and opens again in that worktree.

The rail's search and ⌘⇧N find a chat, open or saved and however old, by its title or by what you and its agent wrote in it, though not by what its tools printed. Each word you type matches the start of a word, and a message has to hold them all. A chat found by its words shows the line that holds them, the words in full ink: under its title in the rail, beside it in ⌘⇧N. Open it and its find bar opens on those words, at the newest place they come. On your phone, the magnifier at the top of a host's agents searches its chats the same way, and opens a chat found by its words with **Find in chat** on them. Sikemux keeps an index of what was said in every saved chat on this computer, and reads only what each chat added since it last looked.

## Going back to a chat

⌘[ brings back the chat you had in front before this one, wherever it was, and ⌘] goes forward again, as a browser does through pages. A chat closed since is passed over. On a browser page that has the keys, the same keys go back and forward in the page instead.

## Tags

Right-click a chat and choose **Tags** to tag it: tick a tag already in use, or **New Tag…** to name one. Once any chat has a tag, a tag button sits in the tab rail's head; pick a tag there to list only its chats, with a pill under the head naming it. Click the pill, or the tag again, to see every chat. Tags stay with a chat while it is open.

## Pinned chats

Point at an open chat in the tab rail and click the pin beside its close, or right-click a chat, open or from the earlier chats, and choose **Pin**. It stays in **Pinned**, right under the running chats, whether it is open or closed, and keeps the name you give it. Click a closed one to open it again. The same pin, or **Unpin** in the menu, takes it off. Drag a pinned chat up or down to put it in another place among them.

Click the heading of **Pinned** or **Recent** to fold it away. A folded group shows how many chats it holds, and stays folded after Sikemux restarts.

## Snoozing and settling

To put a chat out of the way for a while, right-click it and choose **Snooze**: in an hour, in three hours, this evening, tomorrow morning or next Monday, or **Pick a Time…** and type one, such as `fri 2pm`, `tomorrow 8` or `in 90m`. It moves under **Snoozed** in the tab rail, with how soon it wakes, and comes back to the main list at that time, or earlier as soon as its agent asks you something, needs a permission or runs into a problem. **Wake Now** in its menu brings it back at once.

Sikemux settles a chat by itself once you have seen what it last did, it has sat idle for three hours and what it changed is committed; a chat you pinned or are looking at stays. Choose **Settle** in a chat's menu to do the same now. A settled chat moves under **Settled**, folded at the foot of the tab rail, and leaves the island and your phone's list; each settle shows **Undo**. It comes back by itself when you write to it or its agent asks you something. **Settings → Settled chats** lists every settled chat by project, with **Restore** on each, and **Restore** in its menu does the same. Sikemux leaves a lead in the main list while any agent it started is still there.

## Closing an agent

Closing an agent stops it, however you close it: its tab, its row's close in the tab rail, ⌘W, or **Close** and **Close Others** in a menu. When one is at work, Sikemux asks first. When it started other agents, it asks whether they stop too: **Stop them** closes them with it, and **Keep them** leaves them running on their own.

## Links to a chat

Right-click a chat and choose **Copy Link** for a `sikemux://` link that opens it again, in its project, from anywhere on your Mac. If the link names a folder that isn't one of your open projects, Sikemux asks before opening it, since the agent starts there at once and follows that folder's own settings and hooks.

## Moving a chat to another project

Right-click an agent's tab or its row in the tab rail and choose **Move to Project…**, then pick the project. A chat that hasn't started yet can also move from the project name above its composer.

A Claude Code or Codex chat that has already started moves too, with its history: Sikemux stops it, files its saved conversation under the new project, and resumes it there. Wait for it to finish its reply first. Other agents can move only before their first message.

## Handing a chat to another agent

A chat that has begun can go on with another agent: open the model menu under its composer and pick the agent from the row at the top, such as Codex for a Claude chat. Stop its turn first. The chat stays one conversation, with its history in view, and the new agent starts a fresh session. Your next message takes the chat's words along: your first request, the latest exchanges word for word, and how the commands it ran went, about 16,000 tokens at most. It is a selection, not a summary; what doesn't fit is left out, and the new agent can read the whole chat with Sikemux's tools. The agent's reasoning, tool results and attachments don't go along.

A chat that is asleep hands over what its agent's saved session holds, without the commands. Until you send, a line above the composer says what will go and about how many tokens, and it is still there after Sikemux restarts; **Leave out** sends your message without it. On the phone the handoff shows first in the chat's live strip and its sheet, with the same **Leave out**. `/fork` does the same into a new chat with the same agent and account, leaving this one as it is.

## Moving a new chat to another host

Before its first message, a chat can also move to another host on your account: click the host name under its composer. **Has** lists the hosts that hold a copy of the project, with each copy's folder and branch; pick one and the chat starts there, in that copy, keeping what you typed, its agent, model and effort. **Copy to** lists your other hosts; picking one copies the project there first, then moves the chat onto the copy. Hosts out of reach are greyed out. Files attached to the draft stay on this host, so a chat with attachments doesn't move until you take them off; attach them again once it's there. After the first message the host is fixed.

## If something stops it mid-reply

An agent's reply finishes even if Sikemux's background process crashes, your computer restarts, or the agent's own process dies, and nobody has to be watching. Sikemux opens the agent's saved conversation again, says so in the chat, and asks the agent to check what got done before carrying on, since a step cut off mid-way may not have finished. After a few stops in a row the agent is left stopped, with **Retry**.

After a restart this happens when Sikemux's background process starts again: at login when remote access is on, otherwise when you next open Sikemux.

## When the agent asks you something

When an agent asks you something it can't settle without you, it puts a call to you: a card at the end of its chat, the last thing in it. The card says who asks and how long ago, the question, what you need to know to answer, and a picture when there is one to look at. Its options sit in one block, the one the agent would take chosen from the start and marked with Sikemux's **S** and **pick**. Click another to choose it, or click the chosen one again to clear it. The block's last row is a field: with an option chosen it adds a note that goes with it, and with none chosen it takes your answer in your own words. Under it, **Against it** gives the strongest point against the pick, and on a call to ship to production, **What runs** opens to show the exact command it runs. **Go with this** sends whichever option is chosen with its note, or your own words alone; `Enter` in the field does the same, except on a call to ship to production, which no key ever sends, wherever you are typing: only a click or tap on **Go with this** does. On a call about taste or direction, **Not mine** hands it back to the agent that leads the asker, or to the asker itself, to decide. The card's last line says what happens meanwhile: **Nothing happens until you answer** when the agent waits, or what it goes on assuming until you answer, in its own words. A call to ship to production always waits. On a call the agent goes on from that offers no options, **Go with this** with nothing typed lets its assumption stand. A call never times out.

While a call waits, the composer reads **Or answer in your own words**, and what you send there answers it, with any files or pictures you attached. A call to ship to production is the exception: only its button passes it, and words you send go to the agent as direction, never as a yes.

When each option has a picture, such as mockups, the pictures sit in a strip above the options: the chosen option's leads, large, and the others wait beside it, smaller. Click a small one to choose its option, and the large one to see it full size. A call that takes several answers has boxes to tick instead, and one that asks for a password or a key has a hidden field: what you type there reaches the agent and never shows in the chat.

Once you answer, the card gives way to one line saying what you chose and what came of it, such as **You chose “Allow it once” · shipped**.

The title bar shows how many calls wait in the project in front, beside its name, as an amber dot and **2 calls**. Click it for the newest call open with its pick chosen and the others a line each under it; click one to open it instead, and **Open chat** goes to the agent that asked. Another project with calls waiting shows an amber dot on its row in the project tree.

On a MacBook's notch, the closed island adds an amber **N calls** to its right wing, counting the calls of every project. When a call arrives, the island drops open on its card for a few seconds, and resting the pointer on it opens on the newest call alone. Clicking the island opens the agents with every waiting call at the top, the newest open as its card; click another call's row to open that one. It is the same card, with the same rows, field and buttons, and **Go with this** answers it there; **Open chat** opens the asker's chat in Sikemux. Answering moves on to the next call. A call that asks for a password or a key offers **Answer in Sikemux** instead. Drop a file on **Answer** while the island lists the agents to answer the question waiting with it.

On your phone, a host's **Calls** tab, beside **Agents** and **Terminals**, lists the calls open in the project in view, each with its project and how long it has waited, and under **Answered** what came of those settled lately. Tap one to open its asker's chat, where the call docks above the composer: the same card with taller rows and **Go with this** across it. When the agent goes on with what it assumed, the card says so above **Go with this**, and on a call with nothing to pick, **Go with this** lets that assumption stand. A call from an agent with no chat on that host, such as one running in a terminal, opens its card right under its row instead. What you send in the composer answers it too, except a call to ship to production or one that asks for a secret, which only the card answers. A call reaches the lock screen in its own words. On one about taste or direction, its options are buttons and **Something else…** opens a field to type an answer: hold the card down on an iPhone, which opens the app to send it; Android shows two of the options and answers from the card itself, without opening the app. Either asks for the phone's lock first; on Android 11 and older the buttons open the app instead. Any other call opens the app.

An agent's assumption that nobody raised to you is not a call. It shows above the composer, where you can correct it; on your phone it sits under the chat's last line, with **Fine** and **Change**.

While the composer is empty, the keys answer the call at the end of the chat, or the card open in the title bar's calls, or an assumption above the composer:

| You press | What happens |
|---|---|
| `1`–`9` | Chooses that option, or ticks it when the call takes several |
| `↑` `↓` | Moves the chosen option, or the one `Space` ticks |
| `Space` | Ticks the option you moved to, when the call takes several |
| `←` `→` | Moves between the assumptions |
| `Enter` | **Go with this**, or picks the assumption's answer you moved to |
| `⌘Enter` | **Go with this**, or sends every assumption's answer once each has one |

While you type a note or your own answer in the card's field, these keys type there, and `Enter` still answers. A call to ship to production is the exception everywhere: on the Mac, the notch and the phones, neither `Enter` nor `⌘Enter` sends it, so a key pressed just as it arrives can't ship anything; its numbers and arrows still move the choice, and only **Go with this** sends it.

When an agent you started yourself asks you something in the reply its turn ends with, anywhere in it and not only at the end, such as "Which of the two names do you want?", Sikemux makes that a question too: it shows with the questions, and your answer goes back to the agent as a message. Sikemux takes a sentence ending in a question mark as a question when it ends its paragraph or list item, or when all that follows it there is what the agent would pick or that it waits for your pick, as in "Which one? I'm leaning A. I won't start until you pick.", and leaves out code, quotes, headings and tables; a sentence never ends inside bold, italics or code, and the question shows without their marks. A last sentence that means nothing alone, such as "Thoughts?" or "Is that okay?", shows the latest real question before it in the reply, or with none, the paragraph it closes. That paragraph is a question to you when it also asks something a yes or a no can't answer, such as "Who owns this?". A reply that asks several things, one per paragraph or list item, makes a question of each, one tab apiece, the way an agent's question tool asks several at once. Your answers go back together once each question has one, in one message that puts every answer beside the question it answers. If you write to the agent before answering them all, the answers you gave go with your message, each shown under it with its question, and the questions you left no longer wait. Each agent's questions wait on you as one batch, the latest, whether it asked with its question tool or in its reply; the inbox and your phone show them one at a time, in the order the agent asked them. It counts in the inbox and on the Dock badge until you answer it, and goes away once the agent starts another turn, because you folded the questions away and wrote to it or for any other reason. Agents another agent leads, and those Auto runs, answer to them instead. Three kinds go back to the agent once instead of reaching you: a question in a turn another agent's message started, which the two agents settle between them, one that says nothing without the chat, such as "Keep them or delete them?" naming nothing, and a choice left to you in the reply, such as "Want me to cache it, or drop it?" or "Say A or B", which agents must ask with their question tool. The agent decides it, or asks you again so that it stands on its own; asking again right after reaches you. A choice that still comes only in the reply shows under **Needs you** with the options it named to tap, such as **A** and **B** for mockups it laid out as A and B, and the one the agent said it would pick.

An offer a yes or a no answers, such as "Want me to commit it?" or "Ship it to dev?", is not a question to you. If one of the project's [rules](/agents/memory/) names what it offers, Sikemux sends the agent back once and the rule decides: the agent does the work if the rule says to, and leaves it if the rule says to wait for you. Otherwise, and in that case too, the agent shows how its turn left things, such as **Done, uncommitted** under its chat with the offer beside it, and you take it up in its chat if you want it.

The arrow at the right of the assumptions' tabs folds them away, so the composer writes to the agent again.

## What a turn showed

When a turn changes a page of the project, such as a `.tsx`, `.vue`, `.html` or `.css` file, and something already serves that agent's copy of the project on this machine, Sikemux opens the page itself and takes it at a phone's, a tablet's and a desktop's width. It does that once the project's check passes on the turn's commit, or when the turn ends if the project has no check or the work isn't committed. The pictures sit under the reply that ended the turn, each width's **Before** and **After** side by side. Before is the last picture of the same page, and there's none the first time. Click one to see it full size. They show the page; they don't prove anything about it.

Sikemux takes them in a view of its own that keeps no cookies or storage, so nothing you're signed in to shows, and only of pages served on this machine. It keeps the latest 60 sets per project, and a closed agent keeps only its latest of each page.

When nothing serves the agent's copy yet, there are no pictures. Done then offers **Try it**, if the project's `sikemux.json` names a process that serves it, for its preview or for running. **Try it** starts that process in the agent's copy, as one of your processes you can see and stop, and opens the page on the agent's desk. Its next turn that changes the page gets pictures.

In a lead's chat, each worker's finished work shows as a row where it finished. The row has the worker's name, what it did, where its work is and how its checks stand, and its pages' pictures under it. **Try it** opens its page from its own copy. **Undo**, on work that has landed, asks it to revert its own landed commits, which Sikemux lists for it; a commit it shares with another agent isn't its alone to take out. The arrow opens its chat. A shared chat shows neither the pictures nor these rows.

## Its desk

Each agent has its own browser tabs on its desk. `⌘J` shows or hides the desk of the agent in front. See [Browser](/browser/desk-tabs/).
